# RTX 5070 gap localization — September 13, 2026

The remaining ResNet-50 training gap is principally on the GPU. Convolution
derivatives dominate, and the bounded tuner does not reach the largest observed
weight-gradient hotspots. This is a diagnostic study, not a new benchmark cohort
or a measured removable-barrier fraction. No production kernel changed.

## Host versus GPU

The completed, uninstrumented cohort has strict searched training medians of
**42.162 ms Meganeura / 13.410 ms PyTorch**, a 3.14x time ratio.

Nsight Systems 2026.4.1 captures the production grouped Vulkan schedule and CUDA
graph nodes. The paired numerical/source/device/preparation/replay gates in
`p3hpc.check_pair(..., diagnostic=True)` pass.

| Diagnostic training quantity | Meganeura | PyTorch |
|---|---:|---:|
| Mean host sample | 44.658 ms | 13.522 ms |
| Host `step` span | 4.381 ms | not separately marked |
| Host `wait` span | 39.902 ms | not separately marked |
| GPU interval sum / call | 39.736 ms, one grouped submission | 13.312 ms, 632 kernels |

All 1,896 measured CUDA training kernels have graph-node IDs. GPU work is inside
complete host samples. The CUDA intervals include some overlap; neither their sum
nor Vulkan's grouped interval can be subtracted from wall time to obtain busy CPU
time or removable barrier cost. Nevertheless, CPU encoding cannot explain the
threefold training difference: Meganeura's device interval alone is much longer
than PyTorch's complete host sample.

The reference's named wgrad kernels sum to 2.867 ms/call, dgrad to 3.173 ms;
NCHW-to-NHWC and reverse conversions sum to 0.240 and 0.427 ms. These are name-based
aggregates, not complete operator costs. The strict reference visibly uses f32
cuDNN/SIMT kernels; reduced-precision tensor cores are not the explanation here.

## Native dispatch localization

The separate structured capture uses calibrated timestamps and one pass per
dispatch. Normal training is 42.116 ms, instrumented wall time 48.896 ms (1.16x),
and the median total GPU pass interval is 45.745 ms. There are 512 dispatches and
273 barrier groups. Shares below use the sum of dispatch medians, not ordinary
wall time and not isolated shader execution time.

| Direction/family | Dispatches | Sum of dispatch medians | Share |
|---|---:|---:|---:|
| Convolution weight gradients | 53 | 24.890 ms | 54.4% |
| Convolution input gradients | 52 | 10.486 ms | 22.9% |
| Convolution forward | 54 | 6.387 ms | 14.0% |

The twelve `Conv2dGradWeightGemmSmall:scalar` dispatches alone account for
15.588 ms (34.1%). The slowest, dispatch 508 / origin 826, remains **4.475 ms**.
It launches `[5,2,1]`: ten workgroups on a 48-SM GPU. The stem computes a
`[64,147]` weight gradient with reduction length `4*112*112 = 50176`.
This is a structural parallelism limit, not a measured barrier fraction.

The final cuDNN wgrad launch in the matched CUDA trace uses `[5,2,100]`, or 1,000
blocks, with 64 threads/block, 81 registers/thread, and 2,304 shared bytes/block.
Its mean kernel duration is 0.1092 ms. Its association with the stem is an
inference from ordering and geometry, not retained operator correlation. Do not
publish 4.475/0.1092 as an operator speedup: instrumentation differs and CUDA's
conversions/final reduction must also be charged.

## Short native Graphics capture

Nsight Graphics 2026.3.1.0 starts via its SDK after training warmup, with a 200 ms
maximum and three-submit limit. The recorded trace spans 122.733 ms and includes
a complete GPU-projected `meganeura/training/measure/meganeura/sample` interval
of 40.6353 ms. Normal grouped dispatching is retained; `--time-every-action` is off.
The 256 bandwidth limit yields an actual **100 MB PMA buffer**, 54,674 ns counter
sample period and 16,384-cycle warp sampling interval. No event-loss warning was
reported; the target produced complete JSON before the tool's final teardown.

Metrics in that complete sample, from `GPUTRACE_REGIMES.xls`:

| Metric | Peak-normalized value |
|---|---:|
| SM throughput | 32.12% |
| DRAM throughput | 6.07% |
| Active compute warps | 31.07% |
| Long-scoreboard (L1TEX dependency) stalled warps | 9.24% |
| Short-scoreboard stalled warps | 3.51% |
| Workgroup-barrier stalled warps | 1.92% |
| Incoming PCIe traffic | 0.015% |

The throughput metrics have different hardware ceilings. Warp metrics use peak
warp slots over elapsed time; **1.92% is not Vulkan resource-barrier overhead**.
Low DRAM throughput excludes bandwidth saturation as the obvious whole-range
explanation, not memory latency or shared-memory inefficiency. These aggregate
counters corroborate underutilization; they do not assign a cause to each shader.
See NVIDIA's [GPU Trace](https://docs.nvidia.com/nsight-graphics/UserGuide/gpu-trace-ui.html)
and [shader-profiler semantics](https://docs.nvidia.com/nsight-graphics/UserGuide/shader-profiler.html).

The shared-context control and Graphics runner have identical retained output
fields. They match the original-context runner's full logits SHA and 366 retained
numeric values to at most 6.94e-18 JSON-rounding difference. The dispatch-profile
record matches the qualified Systems record exactly. This verifies the recorded
outputs/gradient norms, not every gradient element or a training trajectory.

## What the tuner misses

An additional run of the **unchanged production binary**, without a GPU profiler,
enables only the existing tuning log and NVTX markers. Training visits **5/71**
eligible classes in 2.005 s, completing 22 comparisons. The small-output weight
gradient family is never visited. Graphics and its shared-context control visit
4/71 classes; instrumented preparation can change coverage and selected variants.
Do not interpret differences between these runs as performance improvements.

The source sorts classes by repeated arithmetic volume (`members * M * N * K *
batch_dispatches`). This favors big, repeated contractions but misses operations
with little output parallelism and disproportionately high time per operation.
Most of the two-second budget is spent trying several tile/staging combinations
for each of the first few classes. The dispatch profile confirms that selected
constant-indexed/K=16/K=32 variants are present, while the largest dW hotspots
retain their ordinary scalar pipelines. This is not evidence that tuning is off
or that legal alternatives never win.

The next general experiments should therefore be:

1. Prioritize measured expensive classes and broaden early coverage within the
   existing budget, before spending it on every variant of the first few classes.
   Charge the diagnostic/probe cost; do not add model/card-specific ordering.
2. Revisit parallel/split reductions for small-output, long-K weight gradients.
   Ten workgroups cannot exploit the card regardless of launch batching. Retain
   the existing full-output numerical gates: earlier split-K experiments failed
   accuracy qualification, so this is an engineering target, not a ready promotion.
3. Inspect staging/indexing of the remaining dX/dW hotspots. Do not infer that
   fewer workgroup barriers or a blanket larger K tile will improve performance.

No production change or speedup is claimed. The paper's cohort remains frozen.
